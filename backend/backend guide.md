# Gym App — Backend Execution Guide

**Stack: Node.js + Express + PostgreSQL + Prisma ORM**
**Owner: Backend developers (2 people)**

---

## What the Backend Does

The backend is the brain of the whole system. Both the mobile app (members) and the web dashboard (gym admins) talk to this. It handles all user accounts, gym data, bookings, and payments. Nothing gets stored or processed without going through here.

---

## Why Prisma

Instead of writing raw SQL queries, we use Prisma as our database layer. Prisma gives us:

- One clean `schema.prisma` file that defines all our tables in plain, readable language
- Auto-generated migrations (it writes the SQL for us)
- A built-in database browser (`prisma studio`) — open your database in the browser and inspect/edit data without any SQL client
- Type safety — it knows the shape of every table and will catch mistakes before they reach the database

## Database Schema (prisma/schema.prisma)

This single file defines your entire database. Write all of the following models into it.

```prisma
model User {
  id         Int       @id @default(autoincrement())
  name       String
  email      String    @unique
  phone      String?
  password   String
  photoUrl   String?
  fcmToken   String?
  createdAt  DateTime  @default(now())
  bookings   Booking[]
  payments   Payment[]
}

model GymAdmin {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  password  String
  createdAt DateTime @default(now())
  gyms      Gym[]
}

model Gym {
  id          Int       @id @default(autoincrement())
  adminId     Int
  admin       GymAdmin  @relation(fields: [adminId], references: [id])
  name        String
  address     String
  latitude    Float?
  longitude   Float?
  openingTime String    // stored as "HH:MM", e.g. "06:00"
  closingTime String
  capacity    Int
  photos      String[]
  amenities   String[]
  isActive    Boolean   @default(true)
  createdAt   DateTime  @default(now())
  packages    Package[]
  bookings    Booking[]
}

model Package {
  id           Int       @id @default(autoincrement())
  gymId        Int
  gym          Gym       @relation(fields: [gymId], references: [id])
  name         String    // e.g. "Monthly Premium"
  type         String    // 'daily' | 'weekly' | 'monthly' | 'annual'
  price        Float
  durationDays Int
  benefits     String?
  isActive     Boolean   @default(true)
  createdAt    DateTime  @default(now())
  bookings     Booking[]
}

model Booking {
  id         Int      @id @default(autoincrement())
  userId     Int
  user       User     @relation(fields: [userId], references: [id])
  gymId      Int
  gym        Gym      @relation(fields: [gymId], references: [id])
  packageId  Int?
  package    Package? @relation(fields: [packageId], references: [id])
  slotStart  DateTime
  slotEnd    DateTime
  status     String   @default("pending")
             // 'pending' | 'confirmed' | 'cancelled' | 'checked_in'
  qrCode     String?  @unique
  createdAt  DateTime @default(now())
  payment    Payment?
}

model Payment {
  id               Int      @id @default(autoincrement())
  userId           Int
  user             User     @relation(fields: [userId], references: [id])
  bookingId        Int      @unique
  booking          Booking  @relation(fields: [bookingId], references: [id])
  amount           Float
  currency         String   @default("ETB")
  status           String   @default("pending")
                   // 'pending' | 'success' | 'failed' | 'refunded'
  chapaTxRef       String?  @unique
  chapaCheckoutUrl String?
  createdAt        DateTime @default(now())
}

// Phase 2 placeholder — table exists, nothing built on top of it yet
model Trainer {
  id        Int      @id @default(autoincrement())
  gymId     Int
  name      String?
  bio       String?
  createdAt DateTime @default(now())
}
```

After writing this, run:

```bash

npx prisma generate
```

This creates all the tables in your PostgreSQL database and generates the Prisma client you'll use in your code.

## Using Prisma in Your Code

Import and use the Prisma client in your controllers:

```javascript
// src/config/prisma.js
import { PrismaClient } from "@prisma/client";
const prisma = new PrismaClient();
export default prisma;
```

```javascript
// Example: get all active gyms
import prisma from "../config/prisma.js";

const gyms = await prisma.gym.findMany({
  where: { isActive: true },
  include: { packages: true }, // also fetch related packages
});

// Example: create a booking
const booking = await prisma.booking.create({
  data: {
    userId: 1,
    gymId: 2,
    packageId: 3,
    slotStart: new Date("2024-05-10T09:00:00"),
    slotEnd: new Date("2024-05-10T10:00:00"),
    status: "pending",
  },
});

// Example: update booking status
await prisma.booking.update({
  where: { id: bookingId },
  data: { status: "confirmed", qrCode: generatedCode },
});
```

### BOOKINGS — `/api/bookings` (protected)

| Method | URL                    | Who calls it       | What it does                      |
| ------ | ---------------------- | ------------------ | --------------------------------- |
| POST   | `/bookings`            | Mobile app         | Create a booking                  |
| GET    | `/bookings/my`         | Mobile app         | User's own bookings               |
| PUT    | `/bookings/:id/cancel` | Mobile app         | Cancel a booking                  |

| POST   | `/bookings/checkin`    | Gym staff web page | Mark booking as checked in via QR |

**POST /bookings body:**

```json
{
  "gym_id": 1,
  "package_id": 3,
  "slot_start": "2024-05-10T09:00:00",
  "slot_end": "2024-05-10T10:00:00"
}
```

**What happens inside POST /bookings (step by step):**

```
Step 1 — Validate that slot_start and slot_end are within gym opening hours
Step 2 — Check capacity using a Prisma transaction with raw SQL lock (see below)
Step 3 — If full → return 409 "Slot is fully booked"
Step 4 — If space → create booking (status: pending) + payment record
Step 5 — Call Chapa to initialize payment
Step 6 — Return the Chapa checkout URL to the mobile app
```

> ⚠️ CRITICAL — Concurrency: The capacity check and booking insert must happen atomically. Use `prisma.$transaction` with a raw SQL lock for this specific query. Without it, two users can simultaneously book the last slot and both succeed — a real-money bug.

```javascript
const result = await prisma.$transaction(async (tx) => {
  // Lock the gym row so no other request can read/write it simultaneously
  await tx.$queryRaw`SELECT id FROM "Gym" WHERE id = ${gymId} FOR UPDATE`;

  // Count overlapping confirmed bookings
  const overlapping = await tx.booking.count({
    where: {
      gymId,
      status: "confirmed",
      slotStart: { lt: new Date(slot_end) },
      slotEnd: { gt: new Date(slot_start) },
    },
  });

  if (overlapping >= gym.capacity) {
    throw new Error("SLOT_FULL");
  }

  // Safe to create the booking
  return await tx.booking.create({
    data: { userId, gymId, packageId, slotStart, slotEnd, status: "pending" },
  });
});
```

Write a test that fires 10 simultaneous POST /bookings requests at a gym with capacity 1 — only 1 should succeed. Do this before building anything else on top of the booking feature.

### PAYMENTS — `/api/payments`

| Method | URL                        | Who calls it      | What it does                      |
| ------ | -------------------------- | ----------------- | --------------------------------- |
| GET    | `/payments/verify/:tx_ref` | Mobile app        | Check if payment went through     |
| POST   | `/payments/webhook`        | Chapa (automatic) | Receive payment result from Chapa |

**Full Chapa payment flow:**

```
1. User taps "Book & Pay" in the app
2. App calls POST /bookings
3. Backend creates booking (pending) + calls Chapa:

   POST https://api.chapa.co/v1/transaction/initialize
   Authorization: Bearer YOUR_CHAPA_SECRET_KEY
   {
     "amount": "500",
     "currency": "ETB",
     "email": "user@gmail.com",
     "tx_ref": "booking-123-1715000000",   ← must be unique
     "callback_url": "https://yourapi.com/api/payments/webhook",
     "return_url": "https://yourapp.com/booking-success",
     "customization": { "title": "Gym Booking" }
   }

4. Chapa returns a checkout_url
5. Backend saves checkout_url + tx_ref to the payment record, returns it to app
6. App opens checkout_url in a WebView — user pays with telebirr, CBE Birr, card, etc.
7. Chapa sends a POST to your webhook with the result
8. Webhook handler:
   IF payment successful:
     → prisma.payment.update → status: 'success'
     → prisma.booking.update → status: 'confirmed', qrCode: generated
     → Send push notification to user: "Booking confirmed!"
     → Send confirmation email
   IF payment failed:
     → prisma.payment.update → status: 'failed'
     → prisma.booking.update → status: 'cancelled'  ← slot is freed
```

## Auth & Security

**Passwords:** Hash with `bcrypt` before storing. Never store plain text.

```javascript
const hashed = await bcrypt.hash(password, 10);
```

**JWT:** Sign with `jsonwebtoken`. Payload: `{ userId, role }`. Expire in 7 days.

```javascript
const token = jwt.sign(
  { userId: user.id, role: "member" },
  process.env.JWT_SECRET,
  { expiresIn: "7d" },
);
```

**Middleware:** One middleware for member routes, a stricter one for admin routes that additionally checks `role === 'gym_admin'`.

## QR Code Generation

After payment confirmed, generate a unique string and store it:

```javascript
import { v4 as uuidv4 } from "uuid";
const qrCode = `GYMAPP-${bookingId}-${uuidv4()}`;
await prisma.booking.update({ where: { id: bookingId }, data: { qrCode } });
```

The mobile app renders this string as a visual QR code. The check-in endpoint looks it up from the database.

## Error Response Format

Always return errors in this shape:

```json
{ "success": false, "message": "Slot is fully booked for the selected time" }
```

Status codes:

- `201` — Created
- `400` — Bad input
- `401` — Not logged in
- `403` — Not authorized
- `404` — Not found
- `409` — Conflict (slot full, duplicate)
- `500` — Server error
